# 音声

`tools/tts/` のサイドカーが動いていれば、台詞は再生前に合成され、口は推定ではなく実音声で動きます。動いていなければ何も変わりません。テキストから組み立てた尺で無音のまま口だけが動く——声を持たない環境と、テストが走っている状態です。

用意するには、`tools/tts/reference/clips/` に WAV を置いてコマンドを 1 つ走らせます。

```sh
make voice         # 必要なら環境を作り、クリップを変換する
make dev           # 他と一緒に声も立ち上がる
make tts           # 音声だけを単体で走らせる
```

クリップだけは自動化できません。その声の持ち主の録音そのものなので、他人のもので代用はできません。雑音のない、話者 1 人の音声が合計 1〜2 分あれば足ります。モデルはコーパスで学習するのではなく、参照を条件として使うからです。`make tts-vet` は何も作らずに検査結果だけを出し、`HASHIDATE_VOICE_DIR` でディレクトリごと——リポジトリの外へも——移せます。

動かしているのは Irodori-TTS です。チェックポイントが `Aratako/Irodori-TTS-v4.1-Small`、その下のコーデックが `Aratako/Semantic-DACVAE-Japanese-32dim` で、声が明日も同じに出るように upstream のコミットを固定して入れてあります。どちらもサイドカーの初回起動時に Hugging Face から取得します。ここに選ぶ余地は無く、無いのは意図的です。差し替えるのは中のモデルではなくサイドカーのほうだからです。[別の声を使う](#別の声を使う)を参照してください。

サイドカーは `tools/tts/.run/speech.sock` の UNIX ソケットで待ち受けます。ディレクトリは自分で `0700` で作り、ポートは 1 つも開きません。呼ぶのはこの機械の制御サーバだけなので——[別の声を使う](#別の声を使う)を参照してください——声に手が届くのはこのユーザーだけです。ランタイムの他の部分がループバックに縛られているのと同じ規則を、いちばん強い形で適用したものです。

制御サーバは起動時に音声の状態を 1 行出し、それが変わればまた出します。パネルにも同じ警告が出ます。配信の途中で応答しなくなったサイドカーは、それ以外の形では見えません。キューは流れ、口も動くからです。

## 発話が始まる前に音声が手元にある意味

完成した take が再生前に手に入ることから 3 つが導かれ、それが合成にかかる 1 秒に見合う理由です。

- **口形トラックを実尺へ引き伸ばす**。推定の定数は比率を作るためだけに使われるので、実測長へ正規化すると定数が消えます。声を再学習して喋る速さが変わってもタイミングが生き残るのはこのためです。この環境では長い行で推定が 15 % 短く、短い行ではもっと大きく外れます。
- **口を音声の時計に乗せる**。フレームは落ちますが音声は落ちないので、フレーム差分を足し込む口は先走る方向にしかずれません。演出の位置も同じ時計を読むので、同じ 1 行で一緒に補正されます。
- **口の開き量を、その take 自身の音量で決める**。デコード済みバッファから 1 度だけ測り、その take 自身の水準で正規化するので、声を替えるたびに調整するゲイン定数がありません。テキストが予測できなかった間で口を閉じるのはこれで、引き伸ばしでは直せない部分の大半を隠してくれます。

合成が始まるのは台詞が**積まれた**時点であって、再生される時点ではありません。3 行まとめて投げれば 3 本が同時に走り、待つのは、続けて喋る中の最初の 1 発話だけです。[まとめて送る](control-api.md#まとめて送る)を参照してください。

声が落ちたり応答しなくても、失うのはその行の音だけです。発話は無音で再生され、キューは止まりません。

## 電子透かし

生成されたすべての take に SilentCipher の電子透かしが入ります。話し声より 50 dB ほど下に位置し、この音声がこのプロジェクトで生成されたものであることを示します。埋め込むのはノイズ除去の**後**です。透かしが住んでいる高さは、除去処理が狙う高さでもあるからです。サイドカーは起動時に実際の take で読み出しを検証し、payload が返らなければ起動を拒否します。印のない音声が出ていくことは、後から気づく問題ではなく起動失敗になります。

音声が 1 秒を切ると payload は読み出せなくなります。方式の性質であってこのパイプラインの都合ではありません。一言だけの発話は実質的に印なしで出ていきます。長さを稼ぐために無音を足す手は使えません。ビューアは渡されたバッファの長さで口を動かすので、透かしのために足した無音は、口が動き続ける時間になります。

## 部屋

生成された音声には空間が乗っていません。参照録音には乗っていました。話し声より 33 dB ほど下の定常的なノイズ床で、モデルはそれを忠実に再現します。参照を再現するのがモデルの仕事なので当然です。これは参照が符号化される前に取り除かれるので、生成される行には最初から届きません。コーデックがその上に足す分は、出力側で取り除かれます。両方あわせて、1 行の S/N はおよそ 32 dB から 50 dB になります。

素材としてはそれが正しく、配信に出すものとしては正しくありません。初期反射のない声は、真空で喋っている声に聞こえるからです。そこでスピーカーへ向かう途中で部屋を足し直します。事故ではなく判断なので、コマンドです。

```sh
yarn ctl room hall
yarn ctl room            # 残響なし
```

`booth` / `room` / `studio` / `hall` の 4 つ。減衰時間を直接指定するのではなく、寸法と吸音率という物理的な記述からインパルス応答を作ります。名前は vocabulary に載り、知らない id は残響なしです。

順序が見た目以上に効いています。口を動かすエンベロープは、この処理の**手前**にある dry の音声から測ります。だから部屋は聞こえるだけで、見えることがありません。口が閉じたあとも部屋は鳴り続け——実際の部屋がそうであるように——割り込みは声を切っても、その声が居た空間までは切りません。長い残響が次の行に被るのは事実で、`hall` は 1 秒以上鳴ります。それがホールというものであり、既定にしていない理由です。

音の部屋は、キャラクターが**見えている**部屋とは別の軸です。マイクが動いたように聞こえさせずに、背景だけ切り替えられます。[ステージ](stage.md)を参照してください。

## 別の声を使う

レンダラは音声合成と直接やりとりしません。自分のオリジンに音声を求め、制御サーバがソケットへ中継します。つまり合成器はインターフェースの向こうにいて、埋め込まれてはいません。言語モデルをランタイムの外に置いているのと同じ形です。

契約はルート 2 つです。

| ルート | 受け取るもの、返すもの |
|---|---|
| `POST /speak` | `{ text, reading? }` を受けて、WAV を返す。 |
| `GET /health` | モデルが読み込めているか、何の上で動いているか。 |

これに答えられるものなら何でも代わりになります。向き先は `HASHIDATE_TTS_SOCKET` で変えられ、声を比べるために 2 つ目を並べて走らせるときもこれを使います。`HASHIDATE_TTS_PORT` を渡せば中継先は `127.0.0.1` のそのポートになります。普通の HTTP サービスとして書かれた代役はポートを欲しがるからです。中継より上の層は、どちらが答えたかを知りませんし、気にしません。

この 2 つの変数は制御サーバと `tools/tts/server.py` が同じ優先順で読みます。どちらももう一方から教わりません。訊く手段が無いので、ソケットの場所は両方が自力で導ける場所である必要があります。

返ってきた音声の扱いはどちらでも同じです。バッファの長さを測り、口形トラックを実尺へ引き伸ばし、その実測値で口を動かします。素の WAV を返す合成器なら、この処理はすべてそのまま効きます。

## なぜサイドカーなのか

エンジンは音声のコードを持ちません。「喋られた台詞とは何か」を型で述べるだけで、`AudioContext` を持つビューアがそれを実装します。サイドカーは PyTorch のコードベースで、Python 3.11 の独自環境に置き、HTTP 越しに呼ぶだけで import はしません。

ビューアが直接ではなく `POST /api/speech` 経由で呼ぶのは、サイドカーが CORS ヘッダを出さないからです。このオリジンのページからあちらへは届きません。直接呼べるようにする方法は「声側に CORS ヘッダを足す」か「声をループバックから出す」の 2 つだけで、どちらもライセンスの判断です。中継はそのどちらでもありません。
