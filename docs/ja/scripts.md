# 台本

あらかじめ書いておいたターンの並びを、ファイルにしておくものです。

何を喋るかを決める部分はここにはありません。台本とは、誰かがすでに決め終えたもの——デモ、リハーサル、毎週同じ導入——なので、線の向こう側、オーケストレータの出力と同じ側にあります。ランタイムが用意するのは**ターンを書き留める手段**のほうです。それを用意する価値があるのは、これまでの代わりが `yarn ctl say` を並べたシェルスクリプトだったからで、あれでは行ごとのショットを書けませんし、手を入れた瞬間に順番が崩れます。

置き場所は `show/scripts/` です。追跡されているのは `demo.yaml` だけで、そこに置いた他のものはすべてあなたのものです。

```sh
yarn ctl play demo --check     # サーバなしで読んで検証する
yarn ctl play demo            # setup を送ってから、行をキューへ
yarn ctl play demo --replace  # 積んであるものを捨ててから
yarn ctl play demo --hold     # 読み込むが再生しない
yarn ctl play show/scripts/opening.yaml
```

同じ一覧はパネルのキュータブの先頭にもあります。台本が満たすキューのすぐ上なので、押した瞬間に行がその下へ出ます。そちらは既定で一時停止し、切り替えは一覧の隣のトグルです——[録画](recording.md)を参照。

名前を書いた場合は `show/scripts/` の中を探します。拡張子を付けていなければ `.yaml`、`.yml`、`.json` の順で試します。区切りが入っていれば、あるいは絶対パスであれば、書いてあるとおりの場所を読みます。つまり作業ディレクトリの台本は `./opening.yaml` と書きます。

## 台本の中身

```yaml
title: 導入
note: |
  このファイルを開いた人のためのメモ。送られませんし、読み上げられません。

setup:
  - cmd: reset
  - cmd: idle
    on: true
  - cmd: place
    avatar: { anchor: bottom-right, width: 0.32 }

lines:
  - text: "[hello]こんばんは。"
    stage:
      camera: bust
      backdrop: dusk

  - text: "[explain]今日はこの話をします。"
    stage:
      deck: intro
      slide: 1
```

半分ずつに分かれているのは、寿命が違うからです。`setup` は何か喋る前に一度だけ適用されるもの——どのアバターか、何を着ているか、フレームのどこに絵を置くか。`lines` はターンで、1 行ずつが自分の届けられるショットを持ち歩きます。

この分け方はコマンド体系がすでに持っているもの、ターンより長く残るものと、ターンと一緒に解かれるものの区別と同じです。[コマンド](commands.md)を参照してください。

## 語彙を増やしません

1 行は**ターンそのもの**です。`say` のペイロードを、フィールドごと、スキーマごと。`setup` の 1 項目は**コマンドそのもの**で、通信で送られるときとまったく同じ書き方をします。

代償として `setup` は文章ではなく `cmd:` の並びになります。それでいいのです。カメラの画角に独自の言い方を持つ台本形式は、リリース周期の違う 3 プロセスがずれていくための第二の方言になります。`src/protocol` はまさにそれを防ぐために存在します。この書き方なら、ファイルには実際に送られるものが書いてあります。

`setup` に書けない動詞が 4 つあります。`say`、`queue`、`interrupt`、`clear` です。どれも「これから積む状態」ではなく「進行そのもの」の話で、これから台本が満たそうとしているキューと競合します。

## 行はキューに積まれます

`say` として直接送るのではありません。`play` をシェルのループより値打ちのあるものにしているのがここです。

キューは制御サーバ側にあります。ビューアを再読み込みしても残り、流れている最中にパネルから編集でき、そして次の行の音声を今の行を喋っている間に用意できるだけの深さがあります。1 行ずつ送って待つ呼び出し側は、行と行の間で毎回 1.2 秒ほど黙ることになります。まとめて渡せば 0.3 秒です。それが成立するのは、ショットが行に載っているからです。

積まれた各行には台本自身の名前が刻まれます。台本の区間と、コメントへの返答と、手で打った 1 行が同時に並んでいても読めるようにするためです。[操作面](surfaces.md)を参照してください。

## 読み込んだまま止めておく

`--hold` は再生せずに行だけ積みます。`yarn ctl resume` で解放します。一時停止が届いた時点で喋っている行は最後まで喋り、何も捨てません。

止まっているのはキューの進行だけで、準備は進んでいます。行の音声は再生時ではなく**キューに入った時点**で作られるので、止めているあいだに台本全体の合成が進みます。解放した瞬間に一行目が出るのはそのためで、そこで初めて合成を待つ 1 秒あまりは入りません。

録画したい一本にはこれが要ります。パネルはこの性質の上に手順を組み立てています。単体でも使えます——本番の 1 分前に積んでおいた台本は、一行目が待ち時間から始まりません。

## `--check` が編集のループです

ファイルを読み、通信で使うのと同じスキーマで全行を検証し、実際に送られる内容を表示します。サーバもレンダラも要りません。だから編集の合間に走らせるのはこれです。

台本は生放送に向けて流すものです。送る直前に 1 行ずつ検証していたのでは、9 行目で止まったときにはすでに 8 行が電波に乗っています。

```
$ yarn ctl play demo --check
hashidate はこういうものです  —  /…/show/scripts/demo.yaml
setup   reset, idle, look
lines   22
  1  [hello]こんばんは。今日は、わたしが動いている仕組みそのものの話をします。
      stage camera=bust backdrop=dusk room=room
  …
```

## デモ台本

`show/scripts/demo.yaml` は、ランタイムが自分自身を 2 分ほどで紹介するものです。同時に実例でもあります。話題にした機能をその場で使うように書いてあるので、キュー記法は文の途中で実演され、ショットの話をする行でショットが変わり、響きの話をする行で響きが変わります。

アバター名も、描かれた表情も、重ねる効果も出てきません。それらは特定のモデルのデータで、クローンしたてのリポジトリにモデルは入っていないからです。それを使ったデモは、書いた機械でしか動かないデモになります。

出す資料——`show/slides/hashidate.pdf`——のほうは同梱してあります。このランタイムについての 5 ページで、公開できるものだからです。作成元は別のスライド用リポジトリなので、クローンした側で組み直す手順はありません。ここに置くべきなのは組み上がったファイルのほうです。
